## Domain and operation rules

A source Java `int` field/member has representable values `[-2^31,2^31-1]`; native
transport may sign-extend it to i64 but must range-check on import, never narrow. A
Java `int` add/subtract/multiply wraps modulo 2^32 exactly where that operation occurs.
That source behavior is not a general legal-action clamp. A native allocation/encoding
exhaustion is an administrative fault, not wrap, clamp, defeat, dropped content, or retry.
A field's observed value is its value at the stated read checkpoint; it is not a frozen
constructor snapshot. Resolution-time writes are owned by the original target/instance,
and must not be replaced by a pre-resolution cached value. Reset creates a fresh run
state according to that field's actual constructor/default path; it is not a bulk zeroing
of persistent globals or a rollback of already committed source effects.

Java `Z` is exactly 0/1. Object/enum identity is owner-qualified, never an ordinal.
Collection counts/indices are exact source sequence positions; they do not establish a
content cap. Native checked i64 spans/offsets must reject arithmetic overflow
administratively and must not truncate a legal variable-length collection.

### Cost, X, and free-play dimensions

`AbstractCard.cost` is printed/base cost: ordinary nonnegative (including 0), X `-1`,
unplayable `-2`; preserve signed value and sentinel kind. `costForTurn` is a separate
mutable signed-i32 field. Its source setter guards are call-specific: a negative setter
argument does not overwrite an already-negative sentinel; do not coerce it to 0. A
positive mutable combat cost can independently set `freeToPlayOnce`; neither zero cost
nor that flag implies the other. Captured X, base cost, turn cost, free-once, autoplay,
and ignore-total are independent state. Read/write visibility must gate the exact
instance/value; hidden cost masks both value and classification.

### Economy and floating intermediates

Registered shop display/payment amounts are settled signed-i32 values (`StoreRelic.price`,
`StorePotion.price`, shop-card `price`, and `ShopScreen.actualPurgeCost`) at their own
settlement checkpoint. This does not make source binary32 calculation an i32 operation:
price-generation, discount, jitter, restock, percentages, and other float intermediates
retain source binary32 operation order and the precise Java cast/rounding boundary. Never
serialize an intermediate as a settled price or apply a second rounding pass. Java
float-to-int casts truncate toward zero; `Math.round(float)` follows Java's specified
float rounding (including tie behavior), and these operations are not interchangeable.
Unregistered event/reward/composite prices are not inferred and must not be emitted
under property 41. Numeric inability to represent a legal settled value faults
administratively rather than saturating.

### Sentinel, visibility, and owner identity

Burning-elite designation `MapRoomNode.hasEmeraldKey` belongs to a map node; acquired
Emerald key `Settings.hasEmeraldKey` belongs to run progression. They are distinct
booleans with different owners, writes, and lifetime. A node marker does not grant a
key. `AbstractRelic.counter` and power amounts are signed values with owner-specific
sentinels; there is no universal nonnegative counter rule. `AbstractOrb` has no common
`counter` member: no counter may be synthesized from passive/evoke amount. Intent damage
and hit count are only visible when source intent disclosure permits; hidden/suppressed
intent masks both. Property 41 is unemittable until an actual property owner/member,
read point, entitlement, and visibility proof is supplied; absent proof is not a native
property mapped by guess.

## Field-law exceptions and exact numeric distinctions

* `AbstractCreature.addBlock` caps its result at 999 at that method only; another direct
  assignment/path is not clipped by this fact. Energy helper caps likewise remain scoped
  to those helpers. Current HP/max HP, gold, energy and max energy use signed i32; no
  universal nonnegative clamp or invented maximum. Source damage/heal/death and max-HP
  operations own transitions and side effects.
* Card `timesUpgraded` and `misc` are signed i32. Searing Blow increments per actual
  upgrade; no saturation is inferred. Java arithmetic wraps only at each actual source
  arithmetic operation. Constructor/copy/upgrade writes remain separate cases.
* Potion `potency` is signed i32. `getPotency()` is the observation producer where the
  contract names it; Sacred Bark multiplication and narrowing follow that accessor's
  actual source arithmetic order. There is no universal positive bound.
* `AbstractRelic.counter`, `AbstractPower.amount`, orb passive/evoke amounts, actor HP,
  block, intent damage and intent hit count remain owner-specific signed values. A local
  helper clamp/rounding rule is never generalized across these members.
* Gold/card/potion/relic counts, turn/floor/history ordinals and selector counts retain
  exact legal multiplicity. Host allocation/index exhaustion is an administrative
  resource fault; it is not content truncation or a game-defined cap.
* Public history records only facts actually exposed at their checkpoint; private RNG
  counters/history and unrevealed identity are not emitted. Unknown/masked uses zero mask,
  not a plausible numeric zero. A known absence sentinel is permitted only where the
  typed field explicitly defines it (for example typed reference `(0,-1)`).

potency. A0 starts with three slots; Potion Belt adds two live slots. Ordinary obtain
scans belt order, replaces the first placeholder, sets slot/obtained state and flashes;
full belt returns false. Its indexed overload directly replaces its supplied slot.

obtaining; without Sozu, a full-belt claim fails and retains the offer. Combat

targeted use has its own target validation/cancel path. Discard replaces the slot with
a placeholder without use/payload/onUsePotion; Sozu does not prohibit using/discarding

with Sozu remove the offer without obtain. EntropicBrew's combat queued obtains versus

different producer/use/claim checkpoints, not a blanket visibility or acquisition
rule.

## Primary Ironclad upgrade-count reconstruction (75-member bounded law)

This section closes only the upgrade-count domain for the 75 primary red E24 rows

private verification report identifies exact class/member and constructor bytecode

not an all-color card set, and not proof that every red card is legally storable.

For the 74 ordinary owners, construction delegates to `AbstractCard` without
overriding `upgraded=false` or `timesUpgraded=0`. Effective `canUpgrade` is inherited:
red non-CURSE/non-STATUS cards qualify exactly while `upgraded` is false. Each
`upgrade()` checks `upgraded` first and returns without effect when true; otherwise
it performs its concrete upgrade operations and calls `upgradeName()` once. That
helper increments the signed Java int count, sets the separate boolean, and appends
the display suffix. Consequently legal gameplay states are `(false,0)` and
`(true,1)`; repeated ordinary calls are no-ops. Display text is not identity and
the boolean is not the numeric count.

Searing Blow is the explicit exception: its count-taking constructor and `makeCopy`
preserve the count; `canUpgrade()` always returns true; `upgrade()` has no one-shot
guard, applies damage delta `4 + old timesUpgraded`, increments the signed int count,
sets `upgraded=true`, and formats the name with the new numeric count rather than
calling `upgradeName()`. Thus repeated upgrades remain source-legal and advance both
count and damage. A reconstruction descriptor's checked i32/resource failure is an
administrative fault, never a gameplay cap or substitute card result. Preserve other
persisted cost/misc/history fields independently; changing upgrade count/name does
not authorize resetting them. Unknown IDs reject; they do not map to Iron Wave.
