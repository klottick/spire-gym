# Spire Gym 1.1.0

Version 1.1.0 is the first release since the versioned contract freeze took
effect with 1.0.0. It brings faster native and Python stepping, an opt-in compact
Standard observation and two sets of gameplay fixes. Defaults and frozen
fingerprints are unchanged. The rules IDs changed, so records made with 1.0.0
rules no longer replay. Rust is still the only simulator.

## Faster stepping (M37b, M38b)

Internal work only: gameplay, RNG use, observations, masks, records and
returned array bytes are unchanged. Each step clones less state and does less
bookkeeping. A Standard batch step encodes observations straight into the arrays
it returns, on its own workers, and reuses array memory that Python has
released. A slot normally stays on the same worker between calls. Measured on one 16-core
host for Standard A20 with random actions and the dense observation, after
M38e and before the gameplay fixes:

| Path | v1.0.0 | 1.1.0 code (dense) |
| --- | --- | --- |
| Native scalar, actions/s | about 11.0k | about 22k |
| Native batch, 64 slots, 16 workers, slot steps/s (replay recording on) | about 12.1k | about 38k–41k |
| Python `NativeRunBatch.step`, 64 slots, 16 workers, ms per call | about 6.6 | about 1.3–1.4 |

A batch may now hold up to two calls' observation memory between calls; the
[batching guide](https://github.com/klottick/spire-gym/blob/v1.1.0/docs/batching.md#slots-seeds-and-workers)
explains how to keep that low. These are diagnostic figures, not guarantees.
Ranges and method are in the
[performance record](https://github.com/klottick/spire-gym/blob/v1.1.0/docs/performance.md#a20-standard-checks-after-m38e--2026-11-12).

## Opt-in compact observation (M38e)

Pass `observation="compact"` to `NativeRunSession`, `NativeRunBatch`, `RunEnv`
or `RunVectorEnv`. The compact layout keeps the dense layout's groups, columns
and meaning. It uses fewer rows and `int16`/`int32` values: about 137 KB of
arrays per slot instead of 764 KB. On the same host, a 16-worker native batch
reaches about 92k slot steps/s and `RunVectorEnv` about 104k. It has its own
schema (`spire-gym-standard-run-observation-compact-v1`), capacity preset
(`standard-compact-v1`) and fingerprint (`633b9424…`). The fingerprint is now
part of the freeze. A state larger than the compact capacities stops with a
typed `Capacity` fault; values are never truncated. The compact layout is
Standard-only; other profiles reject it. Sessions and batches also
gain `fault_cause()`. See the
[Standard Run API](https://github.com/klottick/spire-gym/blob/v1.1.0/docs/standard-run-api.md#compact-observation-m38e).

## Gameplay fixes

Both sets of fixes are in the shared engine and follow the original game.

- **Combat (spire-3xq).** Berserk at 5 or more stacks grants its full energy.
  A queued Fire Breathing hit keeps the amount it was queued with. A won combat
  opens no further player choice. A choice between a finished card and its
  queued repeat resolves first, then the repeat plays. Each of these cases used
  to fault. Reaching the 999 card-identity limit is now the typed `Unsupported`
  fault on every path; some card-creation paths reported `Invariant`. A step
  that stops at an inconsistent choice is now a retained `Invariant` fault
  instead of a later `InvalidAction`.
- **Shops and rewards (spire-0kr).** With The Courier, a bought item is
  restocked in its own shop row, so after a purchase the row order and action
  candidates differ from 1.0.0. A shop has at most 15 rows. Circlet is priced
  in shops, and a second Circlet reward stacks its counter. Both used to fault.

## Identities and compatibility

| Profile | 1.0.0 rules ID | 1.1.0 rules ID |
| --- | --- | --- |
| Standard | `spire-gym-native-standard-rules-v3` | `spire-gym-native-standard-rules-v5` |
| M10 Heart and Gym66 | `spire-gym-native-m10-rules-v1` | `spire-gym-native-m10-rules-v2` |
| M9 | `spire-gym-native-m9-rules-v2` | `spire-gym-native-m9-rules-v3` |

Records with an older rules ID fail closed with an explicit error; there is no
multi-version replay. The frozen observation, combat-view, card-metadata and
legacy fingerprints are unchanged: Standard Run `bf8e1d11…`, Standard combat
view `5d8147e1…`, card metadata `effbb810…`, M9 `270163f7…`, M10 Heart
`dccc7624…`, M10 policy `28d92d89…`, Gym66 `4c73f7de…` and `5ba729fd…`, and
combat-v1 `8fd66d21…`. The frozen replay digests and Heart pins are the same as
in 1.0.0. The only Python names added
are the `observation` keyword and `fault_cause()`; the `build_info()` keys are
unchanged. The full list is in
[CHANGES](https://github.com/klottick/spire-gym/blob/v1.1.0/CHANGES.md).

## Verify a wheel

1. Import the extension from the target environment and record
   `spire_lab._native.__file__` and `spire_lab._native.build_info()`.
2. Check that `dirty` is `false`, `features` is `["spire-python/extension"]` and
   `profile` is `release`. Then check that `source_digest` and `file_digest`
   match the values published with this release. The version bump alone changes
   `source_digest`, because the manifests and lock files are digest inputs, so
   1.0.0 values do not carry over.
3. Check the wheel and `.so` SHA-256 values published with the release, then
   update consumer pins. Rules-ID pins must move; fingerprint pins stay.

The digests and artifact hashes are published with the GitHub release, not in
this file. There is no PyPI release.

## Known limits added since 1.0.0

- **Red Circlet duplicates.** The original game offers a second Red Circlet only
  once the Boss relic pool is exhausted. A Standard run cannot exhaust that pool,
  so the duplicate is not modelled.
- **Wish after a won combat.** In the original game, a Wish choice that opens
  just before the battle ends can still take Wish's gold. The engine opens no
  choice after a won combat. It is not known to reach that timing window.
- **Dense Python speed.** The dense Python batch step is about 3–5% slower than
  in the intermediate M38b build. The cause is spread across the encoder, and
  the step is still much faster than in 1.0.0.

The 1.0.0 limits still apply: the Heart routes are supplied and are not policy
wins, and no original-runtime fidelity or RNG parity is claimed. See
[delivery limits](https://github.com/klottick/spire-gym/blob/v1.1.0/docs/delivery.md#7-known-limits-by-surface).
